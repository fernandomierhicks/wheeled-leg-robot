# v4 digital twin — 279 mm baseline

This package is the v4 digital-twin workspace described by `DigitalTwin.md`.
It is isolated from every older simulation. Its normal MuJoCo balance/drive/yaw
path and its low-order headless plant both use the schema-driven Python port of
the Teensy control loop. The jump scenario now uses the production
CROUCH/EXTEND/RETRACT/LANDING/HANDOFF state machine, including the additive
forward nudge, live IMU landing detector, and handoff-specific LQR authority.

## Environment setup

From the repository root, activate the project virtual environment and install
the simulator dependencies once:

```powershell
.\.venv\Scripts\Activate.ps1
python -m pip install -r simulation\mujoco\requirements.txt
```

The launcher uses that active interpreter. If a dependency is missing, it now
prints the same recovery command instead of an import traceback.

All commands below run from `simulation/mujoco/`.

## What is authoritative

- Control names/defaults/bounds: `firmware/robot_teensy/protocol/schema.json`.
- Generated twin view: `twin/params_control.py`; never edit it directly.
- Plant constants: `twin/params_plant.py`. Every unmeasured value is listed in
  `PROVISIONAL_FIELDS` with the test that replaces it.
- Robot-matched defaults: `robot_match.json`, regenerated by
  `twin/tools/fit_robot_match.py`. `defaults.py` loads all 171 values directly
  from `software/gui/parameter_exports/Default gains.json`; it does not carry a
  second hand-copied gain set. The report stores a SHA-256 lock of that exact
  snapshot, and the twin refuses to load if the export changes without a refit.
- Mass inventory: the 2026-08-09 scale data gives 3.242 kg without the
  0.276 kg battery and 3.518 kg driving mass. Each measured wheel assembly is
  0.478 kg; body mass excluding wheels is 2.562 kg. A documented 0.653 kg
  residual closes unweighed hardware to the whole-robot measurement.
- Geometry: `params.py` and `physics.py`, using the v4 dogleg dimensions. The
  base CAD contract retains its 5° backoff (+23° to -57°); the robot-matched
  default uses the export's current 1° backoff (+27° to -57°).
- Log decoding and fitness: the existing GUI modules under
  `software/gui/analysis/`; the twin does not reimplement them.

The source plan's printed dogleg transform and its signed `w_perp=-30.354 mm`
are handedness-inconsistent with the stated acceptance anchors. This package
keeps the signed CAD parameter and uses the equivalent opposite local basis in
`physics.py`; the acceptance anchors are regression-tested exactly.

## Jump reproduction and simulation-only tuning

The jump study reconstructs both starts in the latest reference log (ride
height, pitch, pitch rate, wheel speed, and stick velocity), verifies touchdown
against MuJoCo wheel contact, then runs a scrambled-Sobol launch search followed
by focused nudge/handoff tuning. Finalists are repeated with independent sensor
noise and ±15% actuator-conversion sensitivity checks.

```powershell
python -m v4_twin_279mm_baseline.twin.tools.jump_study --samples 128
```

It writes `jump_optimization_report.json`,
`jump_optimization_candidate.json`, and
`jump_optimization_comparison.png` beside this README. The candidate is marked
`SIMULATION_ONLY_DO_NOT_PUSH_UNREVIEWED`: the matched plant still relies on a
provisional ODrive torque conversion and inferred hip transmission scale, so
this is a bench-test starting point rather than hardware acceptance. The tool
never writes robot parameters or communicates with the robot.

The twin mirrors the firmware's EXTEND→RETRACT transition: measured hip
position/velocity seed a 15 ms smooth braking blend before the minimum-jerk
return, and `jump_retract_torque` caps the simulated hip feedback command.

Regenerate the evidence-derived profile from the latest WLOG, then run the
headless MuJoCo stability matrix:

```powershell
python -m v4_twin_279mm_baseline.twin.tools.fit_robot_match
python -m v4_twin_279mm_baseline.twin.tools.validate_robot_match `
  --output v4_twin_279mm_baseline/robot_match_validation.json
```

The 2026-08-10 match uses two trustworthy stationary plateaus to constrain the
battery/unweighed-mass placement and an effective hip transmission curve while
the controller snapshot remains immutable. The latest saved ODrive preset sets
the wheel torque-command/current conversion. At alpha=0.729, the control law falls
in 1.71 s with neutral mass placement and unit torque conversion, and in 3.07 s
with fitted mass placement alone. The ODrive conversion is the correction that
restores control authority. The
combined profile passes ten 10 s cases spanning alpha 0–1, both quiet and with
a +5° pitch perturbation. These are simulation regressions, not hardware
acceptance tests.

All plant corrections remain provisional. The constrained fit places the battery at
the front/lower packaging limits and assigns the 0.653 kg unweighed residual to
the femur bodies as an equivalent inertial lump; it does not claim the printed
femurs weigh 366.5 g. The 3.41×
wheel-torque conversion assumes the documented 70 KV motor and a saved (not
live-read) ODrive `torque_constant=0.04`; confirm it with a live config read and
T2.1 blocked-wheel test before treating simulated torque as calibrated.
The effective reported-to-physical hip torque scale is 1.25 at retraction and
0.593 at extension. It fits the two equilibrium sag/load anchors to within
0.0025 rad and 0.063 N.m, but it is an evidence-matching plant term, not a
measured gearbox efficiency; T2.3/T2.4 must separate linkage, mass, and actuator
effects. The non-equilibrium low-height sample is intentionally not fitted and
still disagrees substantially.

The normal MuJoCo launcher remains available:

```powershell
python v4_twin_279mm_baseline/launcher.py
```

Its gamepad command range now comes from the exported profile-3 limits
(0.75 m/s and 1.5 rad/s), rather than the former simulator-only 3 m/s and
5 rad/s constants.

## Parameter flow

The pull/push tools communicate only through the GUI's existing local
`robot_ctl.py` server. Push is a diff-only dry run by default, is restricted to
`GAIN_ALLOWLIST`, validates current schema bounds, and refuses changed values
outside that allowlist.

```powershell
python -m v4_twin_279mm_baseline.twin.tools.pull_params params/live_robot.json
python -m v4_twin_279mm_baseline.twin.runtime `
  v4_twin_279mm_baseline/scenarios_json/pitch_step.json `
  --params params/live_robot.json
python -m v4_twin_279mm_baseline.twin.tools.push_params params/candidate.json

# Hands-on only, after reviewing the diff:
python -m v4_twin_279mm_baseline.twin.tools.push_params `
  params/candidate.json --apply
```

## Replay and fidelity score

Both modes now run MuJoCo, load the matching sidecar, and output per-channel
NRMSE/RMSE. Open-loop applies recorded wheel torques and post-slew hip setpoints;
closed-loop runs the firmware-equivalent controller from recorded velocity, yaw,
and hip references. Replays use consecutive reset windows so every RUNNING
command is consumed without allowing initial-condition error to grow for the
entire capture. Defaults are 0.1 s open-loop and 2.0 s closed-loop.

Replay fingerprints the log-era sidecar separately from the latest-export lock.
For the reference run the replay hash is
`e5a5dc827750d38dd07eea0e8bbf4ef505623e07c0f03e26adcf58f0209d990d`; the
current-export hash stored in `robot_match.json` is
`d4a963aa3ba747d6e317b5df08947dd6b4ad1511430bf620defec87437b3f3fe`.
This is intentional: historical replay uses the values active during capture,
whereas new scenarios use the latest export. Neither snapshot is fitted.

```powershell
python -m v4_twin_279mm_baseline.twin.tools.replay_wlog RUN.WLOG --mode open
python -m v4_twin_279mm_baseline.twin.tools.replay_wlog RUN.WLOG --mode closed `
  --output-csv ../../data/twin/RUN_overlay.csv
python -m v4_twin_279mm_baseline.twin.tools.replay_wlog RUN.WLOG --mode both `
  --output-json v4_twin_279mm_baseline/robot_match_replay.json
```

For the 2026-08-10 reference run, both modes cover 100% of requested samples.
The two-second closed-loop replay has 2.11 deg pitch RMSE, 0.136 m/s wheel-speed
RMSE, 0.221 rad/s yaw-rate RMSE, and 0.102 m dead-reckoned XY error within each
window. The 0.1-second open-loop replay exposes larger pitch-rate and actuator
errors. These are now tracked fidelity numbers, but not acceptance numbers while
inertia, friction, delay, and absolute actuator scales remain provisional. The
XY reference is wheel/yaw dead reckoning because WLOG contains no global pose.

## Robust firmware-gain optimization

`optimizer/robust_mujoco.py` reuses the `(1+lambda)` ES engine but evaluates the
actual matched MuJoCo model and firmware-equivalent controller. It tunes the
balance LQR, velocity PI/feedforward, yaw PI, running hip hold, roll/differential
hip loop, and FF1/FF2 in stages followed by a joint polish. Physical parameters,
pitch trims, watchdogs, torque limits, and command limits remain fixed.

Each candidate is scored by its worst result across deterministic plant
variations covering wheel/hip authority, pitch inertia, CG, contact friction,
joint damping, sensor/actuator delay, noise, and battery voltage. Optimizer-only
commands are rate-shaped and stay inside the current profile-3 limits. The
controller snapshot is frozen at launch so a concurrent GUI export cannot
silently change a Windows worker's baseline.

```powershell
python -m v4_twin_279mm_baseline.optimizer.robust_mujoco `
  --generations 24 --final-generations 12 --lambda 8 --workers 8 `
  --ensemble-size 4 --validation-ensemble-size 7 --seed 20260811 `
  --output "../../software/gui/parameter_exports/Robust_balance_candidate_2026-08-11.json" `
  --report v4_twin_279mm_baseline/gain_optimization_report.json
```

The 2026-08-11 run changed 27 balancing parameters and passed all 49 final
scenario/plant combinations. Its robust fitness improved from 2.6854 to 1.3070;
worst pitch RMS fell from 7.82 degrees to 2.94 degrees. A deliberate LQR scale
sweep reproduced the upper-gain boundary: the candidate passes at 0.5x and
1.0x, then exceeds the pitch-rate/saturation limits at 1.5x and above. See
`GAIN_OPTIMIZATION_FINDINGS.md` and the machine-readable report for full results.

The delivered 155-parameter candidate has SHA-256
`195f3d6b2ca125e00d22b56c4b9d64ae6d974c68ad2f6a057111d119d347cdd1`.
It is simulation-only. Do not transfer it to hardware until the identification
tests in `HARDWARE_TEST_HANDOFF.md` have replaced the corresponding provisional
plant constants and the candidate passes a restrained, staged hardware review.
It is deliberately separate from `fit_robot_match.py` and `replay_wlog.py`;
neither identification path permits controller gains to vary.

## SIL

`simulation/sil/test_sil_equivalence.py` compiles the production Teensy
`control_loop.cpp` with desktop hardware stubs, executes
`golden_vectors.csv`, and compares the result to `FirmwareController`. This is
the control-port drift gate; it deliberately compiles the real source instead
of a second C++ transcription.

## Current boundary

Implemented offline: v4 geometry, schema params, firmware control port,
MuJoCo balance route, provisional analytical plant, genuine WLOG/sidecars,
GUI-compatible analysis, direct windowed MuJoCo replay, shared scenarios, guarded parameter flow,
robust optimizer, plant-ID firmware hook, SIL, tests, and both MCU builds.

Not claimed: measured mass distribution/CG/inertia/friction/delay/noise,
calibrated wheel torque, hardware fidelity, hardware safety acceptance, jump
fidelity, or GUI-as-live-wire-protocol client. The whole-robot/component scale
inventory is measured; placement of the unweighed residual remains a fit.
