# TX15 radio package

Everything that goes on the RadioMaster TX15's SD card so it can eventually be
the robot's field head, per `tx15-robot-integration-plan.md`.

**No firmware in this directory.** Nothing here changes the robot. The link is
still iBUS; the CRSF swap (plan §0) has not happened. This package is the
radio-side half, staged and validated so it is ready the moment firmware
catches up.

Target verified against the actual radio: **board `tx15`, EdgeTX `3.0.0`,
SD card layout `3.0`, 480×320, stick mode 2, internal module already
`TYPE_CROSSFIRE`.**

## The HUD

`WIDGETS/WLRHUD/main.lua` — an LVGL widget. Full screen on screen 1 of the
model; it also reflows into a half, quarter or tile zone.

Full screen shows state, fault, attitude, `gain_sched_alpha`, wheel velocity,
both hip torques, twelve health-flag chips, ESP32 link, wheel-glitch count,
link quality and pack voltage. In ESTOP a banner takes over the top half with
the fault name, its description, its severity tier and what that tier means you
should do.

**It is read-only.** It never writes to the robot and never touches a channel.
Arm, disarm, ESTOP and the rescue combo stay on physical channels and firmware
interlocks (plan §2: *never put safety on the Lua path*).

### It will say "NO ROBOT TELEMETRY" at first, and that is correct

The HUD reads sensors by name. Two groups:

- **Native CRSF** — `Ptch`, `Roll`, `Yaw`, `RxBt`, `Curr`, `Bat%`, `RQly`,
  `1RSS`, `TPWR`. EdgeTX creates these itself from the standard frames as soon
  as the Teensy emits them.
- **Custom** — `Stat`, `Flt`, `Alph`, `HipL`, `HipR`, `WVel`, `Jump`, `SUp`,
  `Hlth`, `Glch`, `E32`, `Prof`. These need the CRSF telemetry emitter (plan §6
  item 3), which does not exist yet.

Every reading is tagged LIVE, STALE or MISSING and rendered differently:
bright, amber, or grey dashes. `getValue()` returns 0 both for a sensor that
does not exist and for a link that is down, and a HUD that cannot tell those
apart will cheerfully show "pitch 0.0, all good" while the robot is face down
on the floor. Sensor names live in one table at the top of `telem.lua`.

## The sounds

48 files in `SOUNDS/en/WLR/`, 32 kHz / 16-bit / mono PCM: a callout per robot
state, one per fault code, predictive warnings, and synthesised alert tones.
Speech is Windows SAPI (offline); tones are synthesised with numpy.

Faults are tiered exactly as `fault_severity()` in `shared/comm_protocol.h`
tiers them, so you know the recovery before you reach the robot:

| Tier | Sound | Means |
|---|---|---|
| SOFT | single beep + voice | reset and carry on |
| REPOSITION | two-tone + haptic + voice | pick it up, level it, reset |
| GUI_FIX | voice only | fix the param first |
| REBOOT | siren + haptic + voice | power-cycle; reset will not clear it |

Plus three predictive warnings the current stack has no equivalent of: a rising
tone as pitch climbs toward the watchdog (a stall-warning analogue — audible
*before* the ESTOP, in the window where you can still catch it), a hip-thermal
callout after 20 s above 3.0 N·m, and a wheel-glitch-rate callout as
`vel_glitch_count` builds.

The six flat copies in `SOUNDS/en/` are all `wlr`-prefixed on purpose: the
stock EdgeTX pack already ships `armed.wav` and `disarm.wav`, and other models
on your radio use them.

## The theme

`THEMES/RoboBlue/` — near-black slate, cyan-blue accent, all 13 EdgeTX colour
roles (including `QM_BG`/`QM_FG`, which the 2.12+/3.0 theme schema defines).
Backgrounds at 480×320 and 480×272, plus banner and three previews.

All images are generated by `tools/make_assets.py` from one palette dict, so
recolouring the theme is a one-place edit.

## Tools

| Script | Does |
|---|---|
| `gen_robotdef_lua.py` | `schema.json` → `robotdef.lua`. Cross-checks `fault_severity()` and `mode_color()` in C++ and **fails** if they've drifted. `--check` for CI. |
| `make_assets.py` | renders theme images and the model bitmap |
| `make_sounds.py` | builds the sound pack; `--check` verifies coverage and format |
| `check_lua.py` | runs the HUD against a mock EdgeTX API |
| `check_sdcard.py` | cross-checks model ↔ widget ↔ sounds ↔ theme |
| `install_to_radio.py` | copies to the card; dry run by default |

Run all of them:

```
python radio/tools/gen_robotdef_lua.py --check
python radio/tools/make_sounds.py --check
python radio/tools/check_lua.py
python radio/tools/check_sdcard.py
```

`check_lua.py` is the one worth understanding. Syntax-checking Lua proves
almost nothing about a widget, because every interesting code path lives inside
a property function that only the firmware ever calls. It loads the widget
through a mock EdgeTX API, builds it at four zone sizes, and drives it through
twelve scenarios — no link, link but no robot, running, each fault tier, an
unknown fault code, saturated readings, and a scripted flight of state and
fault *transitions* — calling every property function on every frame. It also
enforces the firmware's own strictness (`lua_lvgl_widget.cpp` raises
`Invalid property` for any unrecognised key) and checks that every sound the
annunciator reaches for exists on the card.

It has already earned its keep: it caught a layout branch that wasted a
half-screen zone.

## Things that were nearly wrong

Recorded because they are the kind of thing that costs an evening:

- **`WLRROBOT.yml` would have been ignored silently.** `storage/modelslist.cpp`
  only opens files matching `model<digits>.yml`. Hence `model90.yml`.
  `check_sdcard.py` now enforces it.
- **EdgeTX 3.0 replaced `switchWarningState:` with a `switchWarning:` map.**
  The 2.12 form would have parsed as an unknown key and the power-on switch
  warning — the whole "refuses to boot with ARM made" protection — would have
  silently not existed. Caught by reading the radio's own `model1.yml`.
- **The flat `armed.wav`/`disarm.wav` would have overwritten stock EdgeTX
  system sounds** that other models on the card use.
- **Input order.** The radio declares inputs RETA (I0=Rud). Following its
  convention rather than inventing one keeps the Inputs screen legible.
- **`crsfArmingMode`.** The CRSF module block has its own arming mode and
  trigger. Left at 0 (channel-based) deliberately — a second arming authority
  inside the radio link is exactly the two-sources-of-truth problem the plan
  warns about.

## Not done

- CH11 ESTOP and CH12 spare are staged but inert until firmware reads them.
- The custom telemetry sensors do not exist yet; the HUD degrades to stale.
- No command tunnel, so no Params / Live-tune / Jump pages (plan §2 pages 2–5).
  Plan §8 is right that the tunnel is the main unknown and should be prototyped
  before any UI is designed around it.
- The six RGB function switches SG–SL are unassigned.
- A crouch-biased custom curve on CH3 — there's 30% expo instead. Drawing a
  5-point curve on the touchscreen is safer than hand-editing the curve point
  pool in YAML.
