Robot Face Screen

Three animated concepts for the screen in the FacetFront well. They use only what the CAD already uses: graphite, GLACIER blue, 45° doglegs, raked combs and chamfered plates. Every preview is a 320 × 240 frame limited to the 16 colours the firmware would have, running at 30 fps.

Recommended

A · Visor Eyes on a live circuit

This combines both of your ideas: a high-tech face, and the CAD's line patterns, which never stop moving.

  • It reads from across the room. The lit area is only 41 × 31 mm. Two big eyes are still clear at 1.5 m, where a full-screen circuit (C) turns to grey haze. The small “1.5 m” previews under each concept show this.
  • The trace mouth adds expression and stays a circuit. It's one glowing line with an upper and a lower lip, built only from flat and 45° segments. It can smile, grin open, zigzag or drop into an “O”. See Visor Eyes with a mouth.
  • Every expression is a 45° cut. Angry is a raked inner corner, happy is a chevron and sleepy is a flat lid. These are the same cuts the parts are made of.
  • It's the cheapest to port. Only the drawing is new. The mood, blink and glance timing already in the current face mode can drive it.

Trace

M1 · PICKED

Reads as: expressive, and still a circuit

At 1.5 m: the shape changes are easy to read.

A glowing trace with an upper and a lower lip, so it can open. Every segment is flat or 45°, like the lines on the links. It breathes in a smile and grins wider as the robot speeds up. It opens into a bouncing grin on a jump, jitters into a zigzag on a reject and drops open into an “O” at E-stop. The corners tilt toward wherever the eyes look.

Colours from swstyle.py; shapes from the links' accent rules (traces with 45° doglegs and square ends, raked combs, graphite plates with raked ends). Nothing else appears on the screen.

Visor Eyes

A · RECOMMENDED

Reads as: a character, but a machine one

At 1.5 m: two clear blue plates.
Look
Two chamfered eye plates built from horizontal slats, like the hood's vents, with a glint bar across the top. Traces with raked combs run in from the edges and feed the eyes.
Motion
A blink collapses the slats to a line. Glances move the whole plate, and pulses run along the traces into the eyes.
State
Expression (lid, rake, chevron, scan bar) and pulse speed. Colour changes only for reject and E-stop.
Cost
Two per-pixel octagon fills (about 10k px each) plus about 20 trace segments. The lightest of the three.

Aperture

B

Reads as: a sensor, not a face

At 1.5 m: a ring with a bright centre.
Look
One octagonal iris of eight graphite blades, each with a blue leading edge, in a bezel ring of comb ticks. Traces leave the ring for the edges.
Motion
The iris twists open and shut, the tick ring turns, and pulses stream outward.
State
Aperture size: shut when not linked, tight when running, wide open in a jump. The ring turns faster as activity rises.
Cost
8 blade triangles and 36 ticks. TFT_eSPI has no shape clipping, so the blades are drawn first and the bezel ring is laid over their ends.

Circuit Mask

C

Reads as: a face only at a glance

At 1.5 m: the lanes merge into texture.
Look
The whole screen is routed buses with doglegs and combs. Two sets of octagonal rings around slatted cores read as eyes, and the centre spine reads as a nose bridge.
Motion
Pulses run on every lane and around the rings all the time. A blink is a bright scan line through the rings.
State
Pulse speed, ring brightness and the scan line.
Cost
About 30 lanes, each with a pulse. The heaviest of the three, and the 3 px lanes blur together beyond about 1 m.

Gestures

Short one-shots that play at random in Standby and Running, never the same one twice in a row. Each one starts and ends at the resting pose, so it blends in and out with no seam. Porting it to the ESP32

Nothing in the repo has changed yet. This is the plan if you pick A.

  • A third personality, chosen at build time. config.h already has DEFAULT_DISPLAY_PERSONALITY (0 = data screen, 1 = cartoon face). Add PERS_GLACIER = 2, and wrap the define in #ifndef so platformio.ini can pick the screen without editing the file, the same way as the WiFi toggles.
  • One full-screen sprite at 4 bits per pixel: 38,400 bytes. A 16-bit full-screen sprite needs 153,600 bytes, which won't fit beside WiFi on an esp32dev without PSRAM. That limit is why the data screen is split into four sprites. A 4-bit sprite has a 16-entry palette, the same 16 colours these previews use.
  • No loop points. Motion comes from continuous functions of time (slow sines, eased glance targets, blink times picked by a hash), so nothing ever restarts. Gestures and state changes ease in and out of the resting pose; a state change morphs over 0.35 s. Pulses ride an accumulated distance, so speed changes never make them jump. Startup and Cmd rejected repeat on this page so you can watch them; on the robot they play once.
  • Gestures are cheap. Each one is a duration plus a few lines that nudge the eye parameters; the scheduler is one random() call per gesture.
  • Only fillRect and fillTriangle, plus one per-pixel loop for the eyes. A thick 45° trace is two triangles. The preview code is written that way, so it ports function by function.
  • About the same SPI load as the cartoon face. A full-screen push is at least 15.4 ms on the wire at 80 MHz, so 30 fps is about 460 ms of SPI per second. The current face mode pushes about 28,000 pixels per frame at up to roughly 60 fps, which is in the same range. After flashing, check loop_max_us and udp_send_max_us in the WiFi diagnostics, and drop to 20 fps if they climb.

Not measured yet: TFT_eSPI converts a 4-bit sprite through its palette line by line as it pushes. I expect 25–30 ms per frame, but I haven't verified it. One run of the existing tft_benchmark env with a 4-bit sprite would settle it before any face code is written.

// config.h
#ifndef DEFAULT_DISPLAY_PERSONALITY
#define DEFAULT_DISPLAY_PERSONALITY  0  // 0 data, 1 cartoon, 2 GLACIER
#endif

// platformio.ini  [env:esp32dev] build_flags
    -DDEFAULT_DISPLAY_PERSONALITY=2

// main.cpp
enum DisplayPersonality : uint8_t {
    PERS_ENGINEERING = 0, PERS_FACE = 1, PERS_GLACIER = 2 };

static TFT_eSprite face4(&tft);   // 320x240 @ 4 bpp = 38,400 B
static uint16_t    kPal[16];      // RGB565; [6..11] = glow ramp

face4.setColorDepth(4);
face4.createSprite(320, 240);
face4.createPalette(kPal);
// per frame: draw with palette indices 0..15, then
face4.pushSprite(0, 0);
// on a state change: rewrite kPal[6..11] only
Each preview is an array of 76,800 palette indices drawn with rectangles, triangles and per-pixel octagon tests, then expanded through a 16-entry palette. The ESP32 would take the same steps. Colours: GLACIER white (0.93, 0.94, 0.95), graphite (0.25, 0.27, 0.30), blue (0.13, 0.45, 0.95) from cad/solidworks_api/swstyle.py.
